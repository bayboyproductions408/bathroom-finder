# App store submission

Everything the two stores ask for, filled in against what this app actually does.
Artwork is in `store/`, generated by `node tools/make-store-assets.js`.

---

## Blockers before either store will take it

1. **A public https domain.** A Trusted Web Activity loads your real site — a LAN
   address will not do. See LAUNCH.md.
2. **Google Play developer account** — $25 once.
3. **Apple Developer Program** — $99/year, *and a Mac* to build and upload with.
   You are on Windows: you need a Mac, a rented cloud Mac, or a cloud build service.
4. **A contact email published** in the privacy policy and terms — both stores require
   a working support contact, and Apple requires it for user-generated content.

**Full description** (Play 4000 max):

> Bathroom Finder shows you the bathrooms around you, and — more usefully — tells you

## Ads change your privacy declarations

Right now the app ships **sponsored listings only** — chosen by the map area you are
looking at, with no identifier and no profile. That keeps every answer below true.

The moment you add a real ad network (AdMob or similar), you must revisit this:

- Play Data Safety gains **Device or other IDs → collected AND shared**, purpose
  Advertising, plus a third-party disclosure for the network.
- Apple's labels gain **Identifiers → Used for Tracking**, which moves the app into
  App Tracking Transparency and requires the ATT prompt before any tracking.
- The EU/UK need a consent screen. There is one built (contextual by default,
  personalised only on an explicit yes) but the network must honour the answer.

The clean position — collecting almost nothing — is worth something in itself.
Spending it should be a deliberate decision, not a side effect of adding a banner.

## Google Play — Data Safety form

Answer it exactly like this. It is a legal declaration; these answers match the code.

**Does your app collect or share any of the required user data types?** Yes.

| Data type | Collected | Shared | Optional? | Purpose |
|---|---|---|---|---|
| Name (display name) | Yes | No | Optional | App functionality |
| Photos | Yes | No | Optional | App functionality |
| User-generated content (reviews, corrections) | Yes | No | Optional | App functionality |
| Device or other IDs (the anonymous device token) | Yes | No | Required | App functionality, account management |
| **Approximate location** | **No** | No | — | Used on device only, never transmitted |
| **Precise location** | **No** | No | — | Used on device only, never transmitted |

Location is the one people get wrong. The app *uses* location — Play asks whether you
*collect* it, meaning transmit off the device. It never leaves the phone, so the honest
answer is No. Do not tick it because the app asks for the permission.

Also declare:
- **Encrypted in transit:** Yes (https).
- **Users can request data deletion:** Yes — provide the contact address.
- **Data collection is optional:** Yes, apart from the device token.
- **Committed to Play Families policy:** Not a children's app.

## Play — content rating (IARC questionnaire)

- Violence, sexuality, profanity, drugs, gambling: **No** to all.
- **Does the app allow users to interact or exchange content?** **Yes** — reviews and
  photos.
- **Does it share the user's location with other users?** **No.** Bathroom locations are
  shared; the user's own position is not.
- **Can users purchase digital goods?** No. (Bathroom rentals are simulated and take no
  money. If you ever switch payments on, this answer changes and you will need Play
  Billing for digital goods — physical-world services are different, read the policy.)

Expect **Everyone** or **Teen** depending on how the UGC questions are weighted.

## Apple — Privacy Nutrition Labels

**Data Not Linked to You** (there is no real-identity account, so nothing is *linked*):
- **User Content** — Photos, Customer Support, Other User Content → App Functionality
- **Identifiers** — User ID (the device token) → App Functionality
- **Contact Info** — Name → App Functionality *(a self-chosen display name)*

**Data Not Collected:** Location, Contacts, Health, Financial Info, Browsing History,
Search History, Purchases, Diagnostics.

**Used for tracking?** No. There are sponsored listings, but they are chosen by map
area alone — no advertising identifier, no cross-app profile, no analytics SDK and no
data broker. If you add an ad network this answer changes and ATT applies.

**Permission strings** — Apple rejects vague ones. Use these verbatim in `Info.plist`:

    NSLocationWhenInUseUsageDescription
      Bathroom Finder uses your location to show the bathrooms nearest to you and how
      far away they are. Your location stays on your device.

    NSCameraUsageDescription
      Take a photo of a bathroom to add to a review, so the next person knows what to
      expect.

    NSPhotoLibraryUsageDescription
      Choose a photo of a bathroom from your library to add to a review.

## Apple — the guideline that actually threatens this submission

**4.2 Minimum Functionality.** Apple rejects apps that are "just a website in a
wrapper". A plain WebView of this site is a real rejection risk. What makes the case:

- It works fully offline
- It uses Core Location for a genuine purpose
- It uses the camera to contribute
- It is not a repackaged marketing site — it does something

Do not submit a bare WKWebView. Use Capacitor with the native location, camera and
offline plugins so the app genuinely uses the platform, and say so in the review notes.

**1.2 User-Generated Content** requires all four of these, or automatic rejection:

| Requirement | Status |
|---|---|
| Filter objectionable material | **Done** — on-device checks plus a human queue; nothing publishes unreviewed |
| A way to report offensive content | **Done** — report any photo, review or listing; reported photos come down at once |
| Block abusive users | **Done** — moderator console → People → Block. Their content disappears and they cannot post |
| Published contact so users can reach you | **Missing** — add a real email to PRIVACY.md and TERMS.md |

**App Review notes** — write this in the submission, it prevents avoidable rejections:

> Bathroom Finder is a community map of public bathrooms. Sign-in is not required and
> there is no account; the app works immediately on launch. Location is used on-device
> to sort results and is never transmitted. All user photos pass an on-device content
> check and are then held for human review before anyone else can see them; users can
> report content and moderators can block contributors. The rental feature is
> non-functional in this build and takes no payment.

## Android build

    node tools/make-keystore.js         create the upload key (once)
    node tools/make-assetlinks.js       write .well-known/assetlinks.json

Set your real domain in `android/gradle.properties` (`twaHost`) and in
`android/app/src/main/res/values/strings.xml` (`asset_statements`), then:

    cd android && gradlew bundleRelease

The `.aab` lands in `android/app/build/outputs/bundle/release/`.

**After the first upload**, Play re-signs with their own key. Copy the SHA-256 from
Play Console → Setup → App signing and re-run
`node tools/make-assetlinks.js <fingerprint>`, then redeploy the site. Skipping this is
the single most common reason a TWA opens with an ugly browser bar.

## iOS build

Needs a Mac. Capacitor wraps the same site:

    npm init -y && npm i @capacitor/core @capacitor/cli @capacitor/ios
    npx cap init "Bathroom Finder" com.bathroomfinder.app --web-dir=app
    npx cap add ios && npx cap open ios

Then in Xcode: set the 1024px icon from `store/appstore-icon-1024.png`, add the three
permission strings above, and archive. Point `server.url` in `capacitor.config.json` at
your live site so the app updates when the site does — and note that Apple expects
meaningful native use, so keep the Capacitor Geolocation and Camera plugins rather than
relying purely on web APIs.

## Order I would do this in

1. Deploy to a real domain, and test it there for a week with real people.
2. Ship **Android** first — Play accepts TWAs, review is fast, and the toolchain is
   already on this machine.
3. Only then take on iOS, once the app has usage worth defending under 4.2.
